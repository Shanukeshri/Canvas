COMPLETE FULL-STACK IMPLEMENTATION PLAN
=========================================

This project should be treated as a full-stack implementation project whose UI is already locked. The goal is not merely to make the prototype functional; it should deliberately exercise a broad range of Next.js, TypeScript, authentication, database, realtime, caching, testing, performance, and deployment concepts.

The previously agreed product rules are authoritative. The current UI prototype remains authoritative for everything else, without redesigning it.

1. FINAL ARCHITECTURE
---------------------

Browser
  |
  v
Next.js App Router
  |
  +-------------------+------------------+
  |                   |                  |
  v                   v                  v
PostgreSQL           Redis              Vercel Blob
Prisma               realtime           assets
  |
  +-------------------+
  |
  v
MongoDB Atlas (only if a genuinely useful document-oriented workload remains)

Realtime:
Browser -> Socket.IO -> separate persistent Node-compatible Socket.IO service -> Redis

Hosting:
Vercel for Next.js.
No AWS is required.

----------------------------

Use PostgreSQL for:

Redis should be used for ephemeral/high-speed state:

- online/offline state
- active Group presence
- temporary realtime state
- Socket.IO Redis adapter
- rate limiting
- short-lived caches
- distributed locks only where genuinely necessary

MongoDB is optional. If retained, use it for genuinely document-oriented activity/event history such as ActivityEvent. PostgreSQL remains the source of truth for anything affecting application correctness.

Vercel Blob replaces AWS S3 for audio/assets.

22. TIMER ARCHITECTURE
----------------------

The timer must be timestamp-driven.

Do not make setInterval(() => remainingSeconds--) the source of truth.

Use a dedicated typed Timer Engine.

Store/calculate in milliseconds:
- startedAtMs
- pausedAtMs where applicable
- resumedAtMs where applicable
- durationMs
- elapsedDurationMs
- relevant session timestamps

The displayed timer may show only seconds.

The underlying model remains millisecond precise.

23. TIMER STATE MACHINE
-----------------------

Use strongly typed states:

Timer status:
- IDLE
- RUNNING
- PAUSED
- COMPLETED

Timer mode:
- POMODORO
- STOPWATCH

Pomodoro phase:
- FOCUS
- SHORT_BREAK
- LONG_BREAK
- NONE

Use discriminated unions for TimerState.

24. TIMER COMPLETION RULE
-------------------------

When the current timer reaches zero:

RUNNING
  ->
COMPLETED

It stays COMPLETED.

It does NOT automatically start:
- a short break
- a long break
- the next focus session
- any next phase

The user must manually initiate the next timer.

25. TIMER PERSISTENCE
---------------------

Persist current timer state so:
- page refresh
- tab close
- browser restart

do not incorrectly reset a running timer.

On reopening:

load timer state
  ->
calculate current elapsed time using timestamps
  ->
if elapsed >= duration:
       COMPLETED
else:
       RUNNING

Never use remainingSeconds alone as authoritative state.

26. STOPWATCH
-------------

Implement Stopwatch as a separate timer mode.

Stopwatch has:
- no Pomodoro phases
- no breaks
- no automatic transitions

It creates a FocusSession and contributes to statistics.

27. FOCUS SESSION
-----------------

Every actual timing session creates a historical FocusSession.

Fields conceptually:
- userId
- type
- taskId optional
- groupId optional
- startedAtMs
- endedAtMs
- elapsedDurationMs
- status
- createdAt

A session may be:
- completed Pomodoro
- interrupted Pomodoro
- Stopwatch

All actual elapsed time counts toward statistics.

28. TIMER STATISTICS
--------------------

Statistics are based on actual elapsed duration, not merely completed timers.

Example:
25-minute configured timer
12m 37s worked
restart

Statistics += 12m 37s

Stopwatch duration also contributes.

29. TIMER CHECKPOINTING
-----------------------

Update/persist session information:
- every 5 seconds
- every minute
- on start
- on pause
- on resume
- on stop
- on restart
- on disconnect
- on reconnect
- on completion
- other meaningful timer events

Do not create an enormous historical database row every five seconds. Use checkpoints to maintain current session state efficiently while keeping the historical FocusSession as the authoritative record.

30. SOLO FRIEND FOCUS

31. GROUP TIMERS

Group members' Pomodoro timers are independent.

The Group shares their current timer state/presence only.

- their timer becomes COMPLETED

- no other member is affected

35. TIMER SOCKET EVENTS
-----------------------

Every timer event should include:

- sessionId
- eventType

- eventId
- sequence/version

Do not broadcast a countdown every second.

The receiving client reconstructs the timer from the event timestamp and authoritative state.

36. EVENT ORDERING
------------------

Use event IDs and/or timestamps/versions to prevent stale realtime events from overwriting newer state.

Example:
pause at T1
resume at T2

If pause arrives after resume because of network ordering, the client must not regress to the stale state.

38. PRESENCE
------------

Presence is ephemeral.

Use Redis with TTL/heartbeat-style behavior so crashed clients do not remain permanently online.

- emit offline

Do not use presence as proof of Group membership.
